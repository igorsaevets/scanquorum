## What the tool claims to be

Scanned PDFs contain a text layer produced by some OCR program, often decades ago. Search
tools read it, AI assistants quote it, and nobody verifies it against the page. ScanQuorum
reads the page with several independent OCR engines and accepts a word only when at least two
agree; where they disagree it refuses to decide and shows the reader a cropped image.

The load-bearing claim: **no language model participates in transcription, and this is enforced
by code rather than by a prompt.**

## Answer these six, in order, and be specific

**Q1. Is the central claim true?**
Trace every path by which a character could enter the output. Is there any route by which text
not proposed by an OCR engine reaches the `.md` file or the accepted output? `verify_ai.py`
lets a vision model take part — read `_parse_choice` and decide whether the boundary is real or
whether I have merely made it inconvenient to cross. If you find a hole, name the file and
line.

**Q2. The tie-break fix — is it right, and did I miss a site?**
Four places in the cascade resolved a tie via `Counter.most_common()` or `max()`, both of which
return whichever item a dict yielded first. Measured: 165 of 11,780 distinct decisions (1.40 %)
changed answer when the engines were reordered; 29 changed a digit. Three of the four sites now
fall through to a dispute or use a stated rule; one (`pick_form`) uses "fewest stray marks,
then shortest, then lexicographic" among forms that share a normalised key.

Is `pick_form`'s choice defensible, or is it an arbitrary rule wearing a justification? **Is
there a fifth site I have not found?** Check `decide()` line by line for any other ordering
dependence, including in `align()` and in the `by_sk` grouping.

**Q3. Are the statistical claims honest?**
The README reports 98.65 % → 99.15 % (Horvitz–Thompson, 56 crops) and states plainly that the
improvement is **not significant** (exact McNemar, 4 discordant pairs, p = 0.125). It also
states that the reference standard **cannot see truncation by construction**, because both the
tool and the measurement inherit the same possibly-wrong box, and that 7 of 7 observed errors
were truncations.

Is anything overstated? Is anything understated? Specifically: is it legitimate to publish a
99.15 % figure at all when the largest known error class is invisible to the estimator that
produced it? Argue either way, but commit to an answer.

**Q4. What breaks first for a stranger?**
Someone clones this tomorrow on macOS or Linux with no Tesseract and no GPU. What fails, and
does the failure explain itself? Note that engine adapters raise `ImportError` when the engine
is absent and the pipeline reports "engine NOT available" and warns that fewer than three
voters is not a quorum. Is that handling honest, or does the tool still produce output that
looks authoritative?

**Q5. Prior art — search the web, do not answer from memory.**
The README claims that multi-engine OCR voting is old (ROVER, Fiscus 1997) but that this
combination was not found: voting whose *refusals* are a first-class output, unresolved places
rendered as images for a human, and an architectural bar on LLM transcription.
**Find a project that does this combination.** If one exists the README must cite it. Give URLs
with dates. "I could not find one" is an acceptable answer only if you say what you searched.

**Q6. The commercial and audience question.**
The stated audience is legal departments, finance/audit/compliance, founders, and people
building RAG over scanned documents. Does the README speak to them, or to engineers? Name the
single sentence that would most improve adoption, and the single claim most likely to be
attacked by a hostile reader.
